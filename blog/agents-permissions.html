Agents

Designing AI agents around permissions, verification and trust

The hardest part of an agent is not giving it more tools. It is defining what it may do, when it may act and how a person can verify the result.

Published October 1, 2026 · AELIA AI Editorial

An AI agent becomes useful when it can do more than generate text. It can search, inspect files, call an API, create a task, prepare a document or operate a connected service. That additional capability creates an equally important engineering question: what exactly is the agent permitted to do?

AELIA's agent architecture starts with capability boundaries. A connector should publish a manifest describing its tools, required authentication, scopes, input schema and possible side effects. The runtime can then decide whether a request is allowed before a tool is executed. This is more reliable than giving an agent a large credential and hoping the model behaves correctly.

Permissions should be understandable to people. A user should be able to see that an agent can read a calendar but cannot create events, or that it can read a repository but cannot merge a pull request. High-impact actions can require confirmation. This creates a useful distinction between planning and execution.

Verification is the second layer. An agent can produce an answer that looks convincing and still be wrong. A production agent should therefore be able to return evidence, tool results, validation checks and unresolved issues. For software tasks, verification may mean tests and a diff. For research, it may mean sources and claim checks. For a payment operation, it may mean a confirmation screen before money moves.

Auditability completes the model. Each tool call should have a trace containing the agent, user, connector, timestamp, action, result and status. Sensitive values should be redacted. The goal is not surveillance for its own sake; it is the ability to understand what happened when something fails.

This approach also makes connectors easier to expand. AELIA can add first-party services such as Novella Matrix, SeaChat and AKODE while supporting external systems through the same contract. The runtime does not need a special code path for every provider. It needs a stable tool interface and a permission system.

Long-running agents introduce another requirement: state. A research job might take minutes. A video generation pipeline might take much longer. The user should be able to leave the page and return later. That means jobs need durable identifiers, progress states, retries, cancellation, notifications and a final result.

Agents also need boundaries around memory. Not every tool result should become permanent user memory. AELIA can separate conversation context, project memory and long-term memory, with clear deletion controls. Memory should have provenance so a user can understand where a stored fact came from.

The best agent experience may therefore feel less magical than a black box and more trustworthy because it is visible. A user can see the plan, approve a consequential step, inspect evidence and receive a result. The interface can still be fast and beautiful while the underlying system remains accountable.

For developers, this architecture becomes an API opportunity. An AELIA agent can be created through an API, assigned tools, given a scoped identity and run asynchronously. Webhooks can report status. SDKs can simplify authentication and streaming. Usage can be measured by tokens, tool calls, media generation or other metered capabilities.

Building agents this way also prepares AELIA for an ecosystem. Third-party developers can create connectors without receiving unrestricted access to the user's account. A connector can request only the scopes it needs. Users can revoke access. Admin systems can review suspicious activity. Safety rules can be applied consistently.

The long-term goal is not an agent that does everything without asking. It is an agent that understands enough context to do the right amount of work and knows when a human decision is required. That is a better foundation for personal assistants, business automation and developer agents alike.

AELIA's agent system is therefore being planned as a controlled execution layer: intent, planning, permissions, tools, verification, result and audit. The interface is the visible part. The trust model underneath is what makes the feature sustainable.
